---

Реализуй создание заказа. Логика:
- транзакция должна быть атомарна;
- сумма считается на сервере из цен в БД, не из клиентских полей;
- идемпотентность по паре пользователь + ключ, гонку тоже
  обрабатывай;
- если клиент прислал одну и ту же позицию дважды — схлопни в одну
  строку с суммарным количеством, а не роняй запрос;
- в позициях заказа копируй имя и цену на момент создания, чтобы
  история не плыла при изменении меню;
- после успешного создания публикуй событие в шину. На идемпотентном
  повторе — не публикуй, иначе подписчик получит дубль.

Покрой тестами: happy path, все ветки валидации, дубликат позиций,
snapshot цены, гонку с одним ключом.

---

`UpdateOrderStatus` публикует событие безусловно. Если статус на
самом деле не изменился (клиент прислал тот же самый), мы отправляем
дубль, sample реагирует, снова PATCH, и получается замкнутый цикл.
Пусть репозиторий возвращает признак реально сменился, а сервис
публикует только по нему. Закрой unit-тестом.

---

В транспорте остался `if userID == ""` — эта проверка должна быть в
сервисе, где она уже есть для создания заказа. Вынеси и продублируй
в остальных методах. В роутере оставь только разбор HTTP-обёртки —
UUID, JSON, заголовки. Всё остальное — сервис.

---

Замени polling в demo-сервисе заведения на подписку RabbitMQ.
Routing key сделай мультитенантным, чтобы очередь одного заведения
не получала события другого — это одна из тех правок, которую я
хочу защитить на интервью. Consumer должен правильно отличать
retryable-ошибки (5xx, сеть) от permanent (4xx кроме 409): retryable
возвращаем в очередь, permanent дропаем. При обрыве соединения —
переподключение. Если брокер не сконфигурирован, откатывайся на
polling, чтобы демо работало без RabbitMQ.

Разложи тесты по слоям, как советует методичка Авито. На сервисе —
юниты с моками. На хендлерах — интеграционные через httptest. На

актуальны (git diff после regen).

---

Подключи валидацию входящих запросов против OpenAPI в рантайме.
Хочу, чтобы спека и реализация физически не могли разъехаться:
любой quantity=999 при `maximum: 50` в спеке валился в 400 до входа
в handler. Ошибку валидатора отдавай в нашем формате `{code, message}`,
а не дефолтным text/plain. Bearer-схему пусть валидатор не трогает,
её проверяет наш `partnerAuth`.

Ок, давай приступим к правкам из ревью. Но есть уточнения. По

заказами данные, поэтому мягкое удаление ставим везде, где есть
операция удаления. По цене — может быть просто сделаем `price`?
Единицу зафиксируешь в комментарии к колонке и в описании поля
OpenAPI.

Итоговый план правок:
- фильтр открытости на витрине;
- перейти с кастомного заголовка на Authorization: Bearer;
- добавить отмену заказа и получение истории статусов;
- разбить разные конфликты на разные коды (сейчас всё в одном);
- дубликат позиций в заказе схлопывать, а не ронять запрос;
- readyz не должен раскрывать pg-ошибку наружу;
- мультитенантный routing key в шине;
- consumer правильно классифицирует retries;
- publisher с reconnect на обрыв;
- ограничить размер входящего тела;
- restart-policy для api и sample;
- индекс под запросы партнёра;
- разбить крупные файлы по агрегатам, если ещё не сделал;
- обновить architecture-plan под все правки, добавить ADR;
- `make lint` должен быть 0 issues.

Не пропусти ничего. После каждого этапа прогоняй тесты и E2E-смоук.
